Personal Runners on a Shared Tinkaria

Architecture concept — how each team member uses their own Claude Code account through one shared Tinkaria instance

May 2026 · Internal · Design record from a full decision-tree review

The Problem

Tinkaria runs as a shared instance for the team, but the box it runs on has only one Claude Code account. Meanwhile every member — PM, Designer, QA, and each Dev — has their own Claude subscription. We need each person to run work through the shared instance on their own account, with their own credentials, their own git identity, and their own usage billed to them.

The core idea

The runner is the user's identity. Each member runs a lightweight tinkaria-runner on their own machine. The shared Tinkaria server holds the board, tickets, context, and UI — the coordination brain. The member's runner holds the credentials and does the work. Credentials never leave the member's machine.

This is feasible because the existing architecture is already ~80% of the way there: Tinkaria's runner already talks to the server over NATS, already registers itself in a KV registry, and already has a RUNNER_MODE=discover seam for externally-launched runners. The work is to make that seam operate across the network, securely, per-user.

The server is authoritative about state (what tickets exist, their branches, PR/CI status). Each runner is authoritative about work and identity (executing Claude Code with the member's account, committing code under their name). The two stay in sync through git and NATS.

Decisions in Detail

1Network transport — Tailscale / WireGuard

The runner is a NATS client that must reach the Tinkaria NATS daemon, which today binds to 127.0.0.1 only (plain TCP + unencrypted WebSocket). We run the whole thing over a Tailscale tailnet; NATS binds to the tailnet interface instead of going public.

Why: WireGuard is purpose-built for the exact failure mode we hit constantly — a laptop roaming between home wifi, office, and coffee shop, sleeping and waking. The tunnel survives IP changes; NATS's own reconnect (infinite attempts, 750ms backoff, 15s ping — already in runner-nats.ts) rides on top. Two layers of resilience, and we write almost no networking code. It also handles encryption and device authentication for free, so we build no TLS.

Most stable connection of the options considered. The cost is operational: every member joins the tailnet. Acceptable for an internal squad. A WebSocket-bridge path (wss://…/runner-ws through the Bun server on :443) is parked for the day we serve external teams who can't assume a tailnet.

2Runner identity — pairing token

A member clicks "Add my runner" in Tinkaria, gets a one-time pairing code, and the runner exchanges it once for a durable per-runner secret bound to their TinkariaUser. Same shape as authorizing a new phone.

Why: It decouples identity from transport. The binding stays correct whether the connection arrives via tailnet today or a WS bridge later — we never redo identity if topology changes. We deliberately did not map identity to Tailscale's node identity: Tailscale is the transport, not the identity provider, or else CI runners and external teams break the model.

Multiple runners per user allowed (laptop + desktop). Registration gains an ownerId; rows can share it. This feeds routing (#3).

3Session routing — sticky default + smart override

Each user has a designated default runner. "Start Session" uses it with zero clicks. A picker auto-appears only when the default is offline or ≥2 runners are online (genuinely ambiguous — wrong machine = wrong local clone).

Offline path (fail-fast): if all the user's runners are offline, Tinkaria blocks with a clear prompt — "Your runner is offline. Start it with tinkaria-runner start, or [use shared runner]." It does not silently queue against a dead runner.

Shared-runner fallback = the team API-key path (separate budget, separate billing) for non-subscribers or emergencies. Failing fast with a reason beats a confusing silent queue.

4Filesystem / workspace — runner clones from the ticket's git coordinates

Today StartTurnCommand carries a workspaceLocalPath the runner just cwds into — which silently assumes server and runner share one filesystem. They no longer do. Instead, the ticket carries git coordinates (repo + base branch + its own working branch), and on "Start Session" the runner materializes the workspace locally.

Consequence accepted

File-level coordination (workspace_claim_create, file-touch conflict detection) loses meaning across separate clones and is redefined as branch/PR-level coordination. Two people on one ticket = two branches, reconciled by git, not a shared file lock. The board becomes git-native: every ticket has its own branch.

This is Symphony's workspace model done right: each member works in their own checkout under their own git identity, so PRs are authored by them — the whole point of personal runners.

5& 6Git write topology, planning docs & PR

Both the server and runners write to git, on disjoint paths:

  • When PM marks a ticket Ready, the server creates the branch (ticket/182-category-filter), commits the planning artifacts (requirements, design, acceptance criteria, gathered context) under .tinkaria/tickets/182/ as a bot identity, and auto-opens a draft PR.
  • The runner later commits product code everywhere except .tinkaria/, under the member's identity.

The branch is the Context Pack carrier — context becomes version-controlled, reviewable, and travels with the branch automatically. The draft PR means the board tracks PR/CI/review threads from "Ready" onward, even before any session starts.

Hazard & guardrail

Two writers on one branch is a divergence risk if planning continues after a session starts. Guardrail: the server writes only under .tinkaria/; the runner writes everywhere else. Disjoint files ⇒ git auto-merges; the runner's rule is simply pull-before-push. No lock protocol.

Planning docs stay in main under one tidy .tinkaria/ tree — the honest git-native choice, no fragile pre-merge stripping step. The server holds a write-scoped GitHub App; it authors only planning docs, never code.

7Presence / liveness — heartbeat TTL

process.kill(pid, 0) is dead across machines, so presence comes purely from the existing NATS heartbeat (every 10s). A runner is degraded after ~25s (2 missed) and offline after ~60s — the intermediate state stops the board flapping on a GC pause or wifi blip.

Payoff of the git-native decision

If a runner drops mid-turn, the session goes suspended, not failed — because the durable state is the branch, not the runner's memory. When the runner reconnects, it resumes from the branch. After 30 min suspended with no runner, the ticket escalates to "needs attention" on the board so it can't silently rot.

8Isolation enforcement — NATS-native per-runner permissions

Pairing tokens (#2) prove identity to the server; they don't constrain the NATS connection, which today uses one shared token. We close this with a server-side auth-callout: the pairing secret becomes the NATS credential, the callout validates it and returns a JWT scoping that connection to only its own subjects (runtime.runner.cmd.{runnerId}.>, its own heartbeat topic, its own registry key). NATS enforces it — not app code.

Scope note

The callout becomes the auth path for all connections — browser WS clients (which fetch a token via /auth/token today) and the server's own orchestrator connection included, not just personal runners. More surface than a column, but it delivers real multi-tenant isolation — which also unblocks the external-team path from #1, since untrusted parties could then safely share the bus.

9Distribution & versioning — bun package + handshake

Shipped as a bun package: bunx @tinkaria/runner — literally the existing src/runner entry plus pairing + tailnet connect. (A compiled single binary is deferred until non-dev / external users exist; the squad already has Bun.)

Versioning: the runner reports protocolVersion in its registration. A runner outside the supported range is marked incompatible (a distinct board state, not "offline"), session start is blocked, and the board shows "run tinkaria-runner upgrade." No auto-update — surprise executable updates on a member's machine are hostile and a security smell.

Never silently degrade. A stale runner must be loudly incompatible, because "mostly works but mangles one field" is the worst debugging experience and it lands on us.

10Profile / capabilities — logical intent server-side, physical + secrets runner-side

Today the server resolves binaryPath (an absolute path on the server's disk — meaningless on a laptop) and ships extraEnv (where API keys would live — violating "auth stays local"). We split it:

Server-defined (travels in command)Runner-resolved (local)
provider, model, effort, planMode, systemPrompt, skills — what to runwhich binary & its path, runtime version — where/how
non-secret team env (optional)Claude auth, API keys, all secrets — never transit the server

binaryPath is dropped from the remote command. The runner advertises its real capabilities in registration (providers + installed versions/models), so the picker only offers options it can honor.

If a ticket asks for a model the runner lacks → refuse with a clear message ("your runner can't run this model — install it or pick another"), never a silent downgrade.

11Workspace bootstrap — declarative hooks, local secrets, cached worktrees

  • Setup is declared in a committed .tinkaria/workflow.md (Symphony's WORKFLOW.md pattern) with hooks — after_create (e.g. bun install), before_run (e.g. bun run build). The server reads it to know the workflow; the runner executes the hooks locally.
  • Secrets are member-local. The runner injects ~/.tinkaria/secrets/<repo>.env into the workspace before before_run. The workflow file references which keys are required, never their values — so the board can preflight-warn "your runner is missing DATABASE_URL" before a confusing failure, while the secret stays purely local.
  • One cached base clone per repo per machine; a git worktree per ticket branch. Warm dependency caches, near-instant ticket switching — reusing Tinkaria's existing workspace_worktree_create machinery, now relocated to run on the runner.

End-to-End Flow

Setup · once Member runs bunx @tinkaria/runner pair https://team.tinkaria.dev → enters the one-time code from the UI → runner stores its per-runner secret → tinkaria-runner start connects over the tailnet, the auth-callout issues a scoped JWT, the runner registers (ownerId, protocolVersion, capabilities) and begins heartbeating.
PM · Ready PM marks ticket #182 Ready. The server creates branch ticket/182-…, commits the Context Pack under .tinkaria/tickets/182/ (bot identity), and opens a draft PR. The board now tracks the PR/CI from the start.
Dev · Start Session Dev clicks Start Session. Routing resolves to their sticky-default runner (online → zero clicks). The command carries logical intent (provider/model/skills) but no paths and no secrets.
Runner · materialize The runner creates a worktree off its cached clone of the repo, checks out ticket/182-… (Context Pack already present as files), injects local .env, runs after_create / before_run hooks, and resolves its local Claude binary — using the member's own account.
Agent · work The agent reads the committed context and implements, committing code under the member's git identity (everywhere except .tinkaria/), pull-before-push. Tinkaria renders the session with its usual rich artifacts; teammates can peek.
If the laptop sleeps Heartbeat stops → runner degraded at 25s, offline at 60s → session suspended, not failed. On reconnect it resumes from the branch. After 30 min → ticket flagged needs attention.
Team · Review → Done Code lands on the draft PR; the server's read of GitHub keeps the board's PR/CI status live even if the runner is offline. Designer/QA/PM review on the ticket. QA can launch its own verification session. PR merges → .tinkaria/ planning trail merges into main with it.

Open Implementation Risks

  1. Auth-callout breadth. Migrating all NATS connections (browser, server, runners) onto callout-issued JWTs is the largest single piece. Sequence it first; everything else assumes scoped creds.
  2. Pull-before-push race. The disjoint-path rule makes merges automatic, but the runner must reliably pull before pushing. Needs a tested helper, not ad-hoc git calls.
  3. GitHub App scope. Server write access to tracked repos is real blast radius. Scope it to branch + .tinkaria/ commits + PR open/status, and audit the bot identity's actions.
  4. Capability advertisement accuracy. If a runner mis-reports installed models, sessions fail at turn time instead of at routing. The advertisement must reflect reality (probe, don't assume).
  5. Preflight secret check. Required-key validation needs the workflow file and the member's local env to agree; a missing key must surface before session start, on the board.
In one line

The shared server is the team's brain (board, tickets, context, draft PRs, status); each member's runner is their hands (their Claude account, their git identity, their machine, their secrets). Tailscale connects them, the branch carries the work, and nothing private ever leaves the laptop.
