How it all fits

Architecture at a glance

Every feature rides on the same spine: a React SPA talks to a Bun server over an embedded NATS bus, the server orchestrates AI CLI subprocesses, and all state is event-sourced to disk. Understanding these four layers makes every feature below predictable.

Client React 19 SPA

Chat UI, virtualized transcript, xterm.js terminals, Zustand stores, Radix primitives, Tailwind 4 theming. Subscribes to topic-based snapshots and sends commands via request/reply.

▲   subscriptions · commands · render-window fetches   ▼

NATS transport embedded daemon

A nats-server subprocess (TCP + WebSocket + JetStream) carries snapshots on KV-backed subjects, command request/reply, and live terminal/turn event streams — with auth tokens, payload compression, and dedup.

▲   publish snapshots · stream turn events   ▼

Server Bun HTTP + WS

Event-sourced JSONL persistence with snapshot compaction, CQRS read models, multi-turn agent orchestration, a separate runner process for turn execution, and PTY terminal management.

▲   spawn · JSON-RPC · PTY   ▼

External subprocesses

Claude Code & Codex CLIs, the Codex app-server (JSON-RPC over stdio), embedded PTY shells, Docker sandboxes, and Cloudflared tunnels for public sharing.

Why event sourcing + CQRS? Writes append immutable events to JSONL logs; reads derive snapshots (sidebar, chat, transcript render-units). Crashing or upgrading mid-turn never corrupts state — the log replays, and clients re-hydrate from the latest snapshot rather than trusting transport order.

Seeing the work

Live transcript rendering

Turning a raw stream of agent events into a stable, scrollable conversation is the hardest UI problem here. Tinkaria splits it into a delivery layer (freshness, caching) and a render layer (virtualization, grouping) governed by a strict projection-key contract so nothing flickers, duplicates, or gets swallowed.

Consumes raw runner turn events and turns them into append-only render facts.

How

Resumes from JetStream/KV state, appends transcript entries to the event store, tracks active status, triggers queue drains, and notifies subscribers of state changes.

Value

A reconnecting client always rejoins a turn already in progress — nothing is lost on refresh.

The spine

Realtime runtime & persistence

Three foundations make everything above durable and live: an append-only event store, an embedded NATS bus, and CQRS read models that turn events into the snapshots the UI subscribes to.

💾 Event store

c3-201 · event-store
What

An append-only JSONL log of all project, chat, queued-turn, and transcript state.

How

Events are appended immutably; snapshot compaction keeps replay fast. State is reconstructed by replaying the log.

Value

Local-first durability — full history, crash safety, and a single source of truth on your disk.

src/server/event-store.ts · events.ts
