Workflow Board

Product concept for Tinkaria — team planning surface that bridges directly into agent sessions

May 2026 · Internal · Draft for squad review (PM, Design, QA, Dev)

Background & Motivation

We studied OpenAI's Symphony, an open-source daemon that polls Linear for issues and autonomously dispatches Codex agents to work on them. Symphony proves a useful concept: an issue tracker can drive autonomous agent execution. But it's a headless Elixir daemon — no team collaboration, no steering, no context preparation. Agents run solo.

Meanwhile, Tinkaria already excels at the session experience: rich artifact rendering, conversational follow-up, sub-agent orchestration, multi-provider support. What Tinkaria lacks is the layer before a session starts — the place where a team plans work, accumulates context per ticket, and hands it off to a dev who launches a session.

Core insight

The biggest context loss in software teams isn't during coding — it's in the handoff between "here's what we need" and "here's an agent working on it." Requirements live in Jira, designs in Figma, discussions in Slack, acceptance criteria in someone's head. The dev reconstructs all of this manually at session start.

The Workflow Board eliminates that handoff loss. The team accumulates context on a ticket. The dev clicks one button. The agent session starts with everything pre-loaded.

What This Is (and Is Not)

This ISThis is NOT
A team planning surface where PM, Designer, QA, and Dev collaborate on tickets before execution begins A Jira/Linear replacement (no epics, sprints, story points, custom workflows, reporting)
A context accumulator per ticket — requirements, design specs, acceptance criteria, technical context, team discussion An autonomous dispatch engine like Symphony (a human always starts the session)
A zero-friction bridge from ticket to Tinkaria session, with all context pre-loaded A standalone PM tool — without Tinkaria sessions, this is a worse Linear
A review surface where session artifacts (PRs, screenshots, test results) flow back to the ticket A dev-only tool — the board is for the whole squad

The Ticket — Context Pack

A ticket is not a Jira clone. It is a structured container where the team deposits everything an agent needs to do the work. Each contribution type has a clear owner.

Context contributions explained

LayerOwnerWhat goes in
Requirements PM What to build and why. User stories, business justification, constraints, scope boundaries. The "what" and "why" — never the "how."
Design specs Designer Visual references: Figma links, annotated mockups, design tokens, component names to reuse, spacing/layout notes. Anything the agent needs to match the intended look and feel.
Acceptance criteria QA Checkboxes that define "done." Testable conditions: "Filter dropdown shows all categories from API," "Empty state displays when no results," "Works at 375px viewport." These directly inform both the agent's implementation and the verification session later.
Technical context Auto-gathered Populated automatically via code intelligence (GitNexus): affected files, blast radius, related recent changes, dependency graph for the relevant code area. The dev doesn't need to explain "the code is in src/server/auth.ts" — the system already knows.
Discussion Team Comments, decisions, resolved questions. "We decided to use the existing Card component, not build a new one." "PM confirmed: no pagination needed in v1." These prevent the agent from re-debating settled decisions.

The readiness indicator

Each ticket shows a completion percentage based on which context layers have been filled. This is the forcing function that prevents the most common failure mode in software teams: a developer starts building before the problem is well-defined.

Why this matters

Without a readiness gate, the default behavior is: PM writes a one-line title, dev picks it up, spends the first 30 minutes of the session explaining context to the agent that the team should have provided upfront. The readiness indicator makes "not ready" visible and socially acceptable — it's not blocking the dev, it's protecting them.

The Bridge — "Start Session"

This is the product's defining moment. When a dev clicks Start Session on a ticket:

  1. The system assembles a Context Pack from all ticket contributions (requirements, designs, criteria, technical context, discussion).
  2. A Tinkaria session opens with the Context Pack injected as initial context — the agent can read it immediately.
  3. The agent already knows: what to build, what it should look like, how it will be tested, what code it touches, and what decisions the team already made.
  4. The dev starts at "let's implement" — not "let me explain what I need."
Key detail

The session is a normal Tinkaria session. All existing features work: rich artifact rendering, follow-up, sub-agent spawning, model selection, plan mode. The only difference is how the session starts — pre-loaded with team context instead of a cold prompt. This preserves Tinkaria's core identity as a conversation-first agent UI.

The ticket on the board transitions to In Session. Team members can see which dev is working on it, how long the session has been running, and optionally peek at live progress.

Artifact Flow-Back

When a session produces results, they attach to the ticket automatically:

ArtifactHow it appears on the ticket
PR createdLink + diff summary + file count. Clickable, opens in Tinkaria or GitHub.
ScreenshotsInline thumbnails rendered on the card. Tinkaria already handles image rendering well.
Test resultsPass/fail summary with expandable detail. Maps to QA's acceptance criteria checkboxes.
Agent decisionsA brief decision log: "Chose X because Y." Visible to the team so they understand the implementation rationale.
Session transcriptExpandable, read-only view for non-dev team members. Full conversational history.

The ticket moves to Review. The team reviews everything where they planned it — no context-switching to GitHub, then Figma, then back to Linear.

How Each Role Uses the Board

📋
Product Manager

Day-to-day

  • Creates tickets in Inbox with requirements: what to build, why, scope boundaries.
  • Checks readiness before moving tickets to Ready. Pings designer or QA if their contributions are missing.
  • Monitors the board for overall sprint health: how many tickets in each column, which are stalled, which are in review.
  • Peeks into active sessions to see real-time progress without scheduling a standup or pinging the dev.
  • Reviews in the Review column: checks that the implementation matches requirements by looking at artifacts on the ticket.

What PM gets

Visibility without status meetings. The board is the standup. Every ticket's state is visible, every session's progress is observable, every artifact is reviewable — all in one place. The readiness indicator prevents premature starts. Cycle time from Ready → Done is measurable per ticket.

🎨
Designer

Day-to-day

  • Attaches design specs to tickets in Inbox: Figma links, annotated screenshots, component references, spacing/layout notes, design tokens.
  • This context flows directly into the agent session when a dev picks the ticket up. The agent sees the mockups and design notes — not a dev's paraphrased interpretation of them.
  • Reviews UI artifacts in the Review column: screenshots of what the agent built, compared side-by-side with the original design.
  • Drops feedback as a comment ("Bottom margin should be 16px not 8px"). The dev can launch a follow-up session with that feedback pre-loaded.

What Designer gets

Design intent reaches the agent directly. Today, a designer puts mockups in Figma, a dev interprets them (often lossy), and the agent never sees the original. Here, the designer's exact specifications are part of the Context Pack. Visual QA happens where the design spec lives.

🔎
QA Engineer

Day-to-day

  • Writes acceptance criteria as checkboxes on tickets before they leave Inbox. These criteria directly inform the agent's implementation (it knows what "done" means).
  • When a ticket reaches Review, clicks "Start Verification Session" — a Tinkaria session opens with the original context plus the implementation artifacts (PR diff, test files, screenshots).
  • Works with the agent to verify: "Run the filter tests with an empty database." "Take a screenshot at 375px width." "Check the API response when category is null."
  • Results link back to the ticket. QA checks off acceptance criteria, moves to Done, or kicks back with notes for a follow-up session.

What QA gets

Acceptance criteria inform the implementation AND the verification. The same checkboxes that guided the agent's work become the verification checklist. QA gets agent-assisted testing in-platform — they don't manually click through the app, they describe what to check and the agent does it. The verification session is a first-class Tinkaria session with full artifact rendering.

⌨
Developer

Day-to-day

  • Scans the Ready column — these tickets have complete context. No guesswork about what's expected.
  • Clicks "Start Session" on a ticket. Tinkaria opens with full context pre-loaded: requirements, designs, acceptance criteria, affected code paths, team decisions.
  • Starts at implementation, not orientation. First message to the agent is "Let's start with the filter component," not "So here's what we're building..."
  • Uses all of Tinkaria's existing features: artifact rendering, follow-up, sub-agent spawning for parallel subtasks, model/provider selection.
  • When done, marks the session complete. PR link, test results, and screenshots auto-attach to the ticket. It moves to Review.

What Dev gets

Sessions start at "let's build" instead of "let me explain." Context preparation is the team's job, done incrementally on the ticket, not a solo activity crammed into the first 10 minutes of a session. The dev also benefits from knowing that acceptance criteria are pre-defined — there's no ambiguity about what "done" means.

Concrete Scenarios

Scenario 1: Standard feature ticket

  1. PM creates ticket #182 Add category filter to dashboard with requirements: what the filter should do, which page, which data source.
  2. Designer attaches a mockup showing the filter placement, a note about reusing the existing Select component, and spacing guidelines.
  3. QA writes acceptance criteria:
    • Filter shows all categories from GET /api/categories
    • Selecting a category filters the dashboard list
    • "All" option clears the filter
    • Filter persists across page navigation
    • Empty state when no results match
  4. Technical context auto-populates: affected files (DashboardPage.tsx, api/categories.ts), blast radius (3 direct callers), related recent change (#174 modified the same API).
  5. Readiness hits 100%. PM moves to Ready.
  6. Dev picks it up, clicks "Start Session." The Tinkaria session opens. Agent already knows what to build, what it should look like, how to test it, what code to touch, and that #174 recently changed the same API. Dev says: "Let's start with the API hook, then the UI component." Session runs with full Tinkaria UX.
  7. Session finishes. PR #350 created, 4 files changed, screenshots attached. Ticket moves to Review.
  8. Designer opens the screenshots, compares with mockup. Spacing matches. Approves.
  9. QA clicks "Start Verification Session." Works with agent: "Run the filter with no categories in the database." Agent runs the test, screenshots the empty state. QA checks all boxes. Approves.
  10. PM confirms requirements met. Ticket moves to Done.

Scenario 2: Rework loop

  1. Ticket #177 reaches Review. Designer notices the notification badge is using red instead of the brand amber.
  2. Designer adds a comment: "Badge should be amber (#F59E0B), not red. See design system tokens." Kicks the ticket back.
  3. Ticket returns to In Session. Dev launches a follow-up session. The agent starts with: the original context + implementation from the first session + the designer's feedback. Dev says: "Fix the badge color per the review comment." Agent makes the one-line change, updates the screenshot.
  4. Ticket returns to Review. Designer confirms. Done.

Scenario 3: Stalled session

  1. Ticket #180 is In Session. The agent encounters a test failure it can't resolve after 2 retries. The card shows an amber dot and "STALLED."
  2. Dev notices on the board. Clicks the card, sees the agent's transcript: it's failing because a test fixture references a removed column.
  3. Dev types a steer message: "The fixture was updated in PR #348, pull main and re-run the migration." Agent resumes, pulls, re-runs. Tests pass.
  4. Session completes normally. Ticket moves to Review.

Integration Strategy

Phase 1: Built-in board

Simple, opinionated, no external dependencies. The board lives inside Tinkaria. Tickets are created and managed here. The team uses the board as their primary planning and review surface for agent-assisted work.

Ship first — this is the core product. It works standalone without any external tracker.

Phase 2: Tracker sync (optional)

For teams that already use Linear or GitHub Issues: two-way sync so the board reflects external tracker state. Issues created in Linear appear on the board with context ready to enrich. Status changes sync both ways.

Ship later — meets teams where they are, but doesn't block the core experience.

Scope guard

Phase 2 does NOT turn the board into a full Linear client. It syncs titles, descriptions, and status. The context enrichment (design specs, acceptance criteria, technical context, discussion) always happens on the Tinkaria board. The external tracker is the source of truth for what work exists; the board is the source of truth for execution context.

Summary

The Workflow Board is not a project management tool and not an autonomous dispatch engine. It is a context accumulator that bridges team planning into agent sessions.

  • For PM: Visibility without status meetings. Requirements reach the agent unfiltered.
  • For Designer: Design specs become part of the agent's working context. Visual QA in-platform.
  • For QA: Acceptance criteria inform implementation AND verification. Agent-assisted testing.
  • For Dev: Sessions start at "let's build" with full team context pre-loaded.
  • For the team: Plan, execute, and review in one place. No handoff loss.
The pitch

Every other tool makes you plan in one place, code in another, and review in a third. Tinkaria's Workflow Board connects all three: the context your team accumulates during planning becomes the agent's working context during execution, and the agent's output becomes the team's review material — all on the same platform.
