mobile-composer-menu — Implementation Notes

Working narrative for docs/stories/mobile-composer-menu/story.md. The story is the contract; this explains how the implementation got there.

Iteration 2 — trigger placement (in-pill icon)

Feedback after iteration 1: the collapsed trigger still occupied a dedicated row below the input pill and the unbound-model label ("Default (recommended)") read long. Considered top-navbar placement, but rejected it: at submit time getComposerSnapshot() reads composerPreferencesRef.current.getSnapshot() (the imperative handle on the mounted ComposerPreferenceControls), which carries provider-lock overrides held in that component's local state. Moving the control to ChatNavbar would null the ref on mobile and silently drop those overrides from the sent message — a correctness regression, not just layout.

Chosen: keep ComposerPreferenceControls mounted in ChatInput (ref/submit intact), but on mobile render it as a compact icon-only trigger inside the composer input pill (leading adornment, left of the textarea) and drop the bottom toolbar row entirely. Desktop keeps the bottom chip row. The mobile trigger is now icon-only (model/mode glyph; Plan Mode blue + Codex Fast Mode emerald preserved); the model name moved to aria-label. The ComposerPreferenceControls element is defined once in ChatInput and placed via isMobile either inside the pill row or in the desktop toolbar (single mount, ref attaches to whichever renders).

What was built

Single-file feature in src/client/components/chat-ui/ChatPreferenceControls.tsx (+ extended ChatPreferenceControls.test.tsx). On mobile (useIsMobile(), ≤767px) the inline chip row collapses into one model-indicator trigger that opens a drill-in Radix Popover (root ↔ category). Desktop ≥768px is unchanged. The shared PopoverMenuItem gained one optional, backward-compatible prop (trailing).

Design decisions (where the spec was ambiguous)

DecisionChoice & why
Desktop safety vs. DRYLeft the desktop JSX completely untouched and added a mobile if (isMobile) return … branch after the hooks. The mobile menu builds from a local categories array. This duplicates the small option-enumeration but makes desktop regression structurally impossible (its code never changed). Chose surgical-safety over the story's "zero duplication" aspiration — see Deviations.
Trigger identityNew additive UI-identity chat.composer.menu (action + popover) for the collapsed trigger, rather than reusing chat.composer.model. Keeps desktop selectors intact and gives the mobile surface its own stable hook for the overlay/e2e.
Drill affordanceAdded optional trailing to PopoverMenuItem to render the › chevron on category rows. Additive prop — the three other consumers (Fork/Merge dialogs, ChatRow) are unaffected.
Skills rowRendered as a PopoverMenuItem with selected={skillsVisible} (highlight = on) and no trailing; onClick toggles the ribbon and closes the menu. Honors "Skills is a toggle, not a value picker."
Trigger state coloringRender-time derivation: Plan Mode → blue + ListTodo icon; Codex Fast Mode → emerald. No Effects.
"Speed" labelCodex Fast Mode category labelled Speed in level-1 (value "Fast Mode"/"Standard") to read as a category name rather than repeating the value.

rule-react-no-effects compliance

  • Menu navigation is local useState (menuOpen, menuCategory) — workflow state, not Effects.
  • Trigger label/icon/color are derived during render from existing props.
  • Menu actions (select, drill, back, toggle, close) are event handlers.
  • useIsMobile() is the existing external-subscription adapter (the one sanctioned Effect boundary).
  • No useEffect/useLayoutEffect added.

Deviations from the plan

Story Design Notes said "reuse existing option-derivation … zero duplication." Implemented with a local categories structure for the mobile path while leaving desktop JSX intact, so the option enumeration is duplicated (small, contained). Rationale: the desktop path is verified-working and higher-risk to break; not touching it is the surgical choice. A future DRY refactor (single categories source feeding both paths) is possible but was out of scope for this normal-lane change.

Tradeoffs considered

Verification (dual-signal)

Unit (bun test ChatPreferenceControls): 6/6 pass — 3 desktop (unchanged) + 3 mobile (collapsed trigger present & chip row absent; Plan Mode blue; Codex Fast Mode emerald). Typecheck: @typescript/native-preview exit 0.

E2E via browser-harness against the live Vite client (:5174, which proxies to the :5175 dev backend — /health green: nats/daemon/runner all ok). At 390px:

  • Collapsed trigger ⬡ Opus ⌄ renders; desktop provider.action absent.
  • Tap → level-1: Provider/Claude · Model/Opus · Reasoning/High · Context/200k · Mode/Full Access · Skills/Shown.
  • Drill into Reasoning → ← Reasoning + Low/Medium/High/Max; select Medium → menu closes; reopen shows Medium.
  • Skills row tap → menu closes; reopen shows Hidden (ribbon toggled).
  • Mode → Plan Mode → menu closes; trigger gains text-blue + ListTodo icon.
  • Resize to 1200px → live switch back to the desktop chip row; the Medium + Plan Mode changes made on mobile are reflected there (same state, same callbacks).
  • 0 console errors / 0 exceptions; dev log clean (upstreamError:0).

Note: a transient test-script bug (a startsWith("Mode") selector matching "Model") was a harness artifact, not an app defect; corrected with an exact-match selector.
