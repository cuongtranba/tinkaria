US-NATSPORT — Pin embedded NATS port normal lane

Why

Every server restart picked a new random NATS TCP port (observed 54355 → 55410). A paired runner bakes nats://host:port into its credential, so each restart silently invalidated the runner — forcing a re-pair, and (when not re-paired) leaving the runner on a dead port → turn timeouts. This is what turned the whole debugging session into a moving target.

Root cause

nats-daemon-manager.ts destructured NATS_PORT out of the environment (NATS_PORT: _natsPort) and never re-added it to the spawned daemon child's env. So even NATS_PORT=4222 was silently dropped, and the daemon (nats-daemon-callout.ts:26, NATS_PORT ? Number : -1) always fell back to an ephemeral port.

Fix

// nats-daemon-manager.ts
NATS_PORT: natsPort,          // was: _natsPort (discarded)
...
env: {
  ...spawnEnv,
  ...(natsPort ? { NATS_PORT: natsPort } : {}),   // pass through when set
}

Opt-in, same pattern as NATS_DATA_DIR. Other NATS env vars stay stripped (intentional isolation). Default (unset) is unchanged → ephemeral.

Verification (live, dev profile)

NATS_PORT=14222 boot  → nats://127.0.0.1:14222
restart (same)        → nats://127.0.0.1:14222   ✓ survived
NATS_PORT unset       → nats://127.0.0.1:59244    ✓ ephemeral (default unchanged)
typecheck: exit 0

Operator note

Add NATS_PORT=4222 (any free port) to the start command. The port must be reachable by remote runners over the tailnet. Pick once and keep it.

Open

This stops the restart→re-pair churn. It does not address "connected but can't use" (the runner heartbeats but a turn times out) — that's the separate credential/clear-error work, which is held pending one clean turn capture (the code already throws a clear error on the no-token path, so the current timeout is a different path that needs identifying before fixing).
