Spike result — Phase 1 (2026-05-26)

Verdict — Path A feasible & preferred

The @lagz0ne/nats-embedded wrapper bundles the official nats-server v2.12.5 (past the 2.10 auth-callout floor) and exposes config:/args: escape hatches. Running the bundled binary directly with an auth_callout config: a normal client got Authorization Violation (callout fires, no responder → denied = server enforces it); the auth_users service account connected (documented bypass). So isolation is enforceable on the embedded path — no external nats-server needed, the ops-change gate is moot.

Caveat — wrapper include bug (drive the binary directly)

The wrapper's websocket:true + config: combo emits include '<abs-path>' into a temp file that nats-server mis-resolves against the temp dir (/tmp/…/Volumes/… → not found). And wsPort discovery only waits when the wrapper's own websocket option is set. Plan: generate our own callout config and spawn the bundled binary (resolveBinary()) directly, discovering ports via stderr / ports-file — the shape nats-daemon.ts already uses.

Resolved — @nats-io/jwt installed and wired

@nats-io/jwt@0.0.10-5 added. The responder decodes the callout request with decode() (it arrives as a JWT, not plain JSON — this was the first integration bug discovered), mints a scoped user JWT via encodeUser(), and wraps it in a signed encodeAuthorizationResponse(). Works end-to-end.

Design decisions (where the concept was ambiguous)

PR1/PR2 seam

The concept sequences "isolation" (PR1) before "identity" (PR2), but per-runnerId scoping seems to need identity. Resolved by scoping only the server-spawned runner in PR1 (the server knows its runnerId at spawn, so it mints the scoped creds), and deferring paired per-user creds to PR2. The subject policy is identical across both, so PR2 reuses it without rework.

Bind + callout land together

Binding NATS to the tailnet without the callout would expose a shared-token bus to every tailnet peer — strictly worse than today. So the tailnet bind is gated behind the callout in the same change; no "temporarily insecure" intermediate state (an explicit stop condition).

WireGuard for confidentiality, keep no_tls

The concept's decision #1 says "we build no TLS" — WireGuard already encrypts. PR1 keeps WS no_tls: true within the tailnet and documents it as a trust assumption rather than adding a TLS layer. Flagged as a stop condition if reviewers want TLS anyway.

Tradeoffs

  • Callout vs static NATS users. Static accounts are simpler but can't scope dynamically-created runnerIds and don't extend to PR2's paired creds. Chose callout as the one seam that serves both; static users kept only as a fallback if the spike kills callout on both paths.
  • Callout on the connect path. Adds one round-trip at connect and makes the responder critical infrastructure (hence added to /health). Accepted: it's connect-time only, steady-state pub/sub is unaffected.

Open questions (each with a recommendation)

Q1 — Embedded auth-callout support? ✓ RESOLVED (Path A)

Answered by the Phase-1 spike: yes. The bundled binary is official nats-server v2.12.5 and enforces auth_callout via a config file. Deliver config by driving the binary directly (not the wrapper's websocket+config combo). See "Spike result" above.

Q2 — Browser identity for ui-client scope

/auth/token is unauthenticated today and there is no per-user browser auth. PR1 wants a ui-client credential, not the admin token.

Recommendation: issue a single broad ui-client class credential in PR1 (no per-user scoping). Per-TinkariaUser browser scoping is out of PR1 scope; revisit if/when browser auth exists.

Q3 — Callout signing-key lifecycle

The responder needs a signing key (new server-held secret).

Recommendation: store alongside nats.token in NATS_DATA_DIR (same trust boundary, gitignored); treat rotation as a documented follow-up, not PR1 scope.

Design decisions (Stage A)

Callout request body is a JWT, not plain JSON

The NATS server encodes the AuthorizationRequest as a JWT and sends it on $SYS.REQ.USER.AUTH. The responder must call decode() from @nats-io/jwt to extract the nats claim containing user_nkey, server_id, and connect_opts.

User JWT audience must be the account name

The aud field of the issued user JWT must equal the account name from the nats-server config (CALLOUT_ACCOUNT), not the default "NATS". NATS uses this to know which account to place the connection in. Error: "No valid account NATS for auth callout response on account CALLOUT_ACCOUNT: account missing".

Allow-only policy (no deny lists)

NATS evaluates allow/deny such that deny always wins over allow (if a subject matches both, it is denied). Using a wildcard deny for runner scope exclusion would also deny the runner's own commands. Solution: use allow-only lists (subjects not in allow are denied by default). This is simpler, correct, and matches NATS's natural model. The integration test confirms isolation.

Stage A credential registry — in-memory token map

Stage A uses a simple Map<token, identity> in the responder. The test registers tokens directly. Stage B wires this into the server's credential-issuance path (minting per-class tokens at startup and per-runnerId tokens at runner spawn).

Deviations from plan

Suggested module layout mostly followed

One addition: nats-daemon-callout.ts is a sibling to nats-daemon.ts (not a sub-module). The original plan said "extend nats-daemon.ts … in callout mode" but keeping them as separate entry points is cleaner for the NATS_AUTH_MODE dispatch in NatsDaemonManager (Stage B).

Design decisions (Stage B)

Stateless signed tokens — no shared in-memory state

The server process (token issuer) and the daemon child (token verifier) share only a 32-byte secret stored on disk at NATS_DATA_DIR/nats.callout-token.secret. Token format: base64url(payload_json) + "." + base64url(HMAC-SHA256(secret, payload_json)). No registration call needed; the responder calls verifyCredentialToken instead of doing a map lookup. This eliminates the Stage A IPC design requirement.

mintToken callback on RunnerManager

Rather than passing the token secret into RunnerManager (which would couple it to the auth-callout module), a mintToken: (runnerId) => Promise<string> callback is added to RunnerManagerOptions. In callout mode the server closes over keys.tokenSecret; in token mode the callback is undefined and authToken is used unchanged. Zero token-mode regression risk.

uiClientToken — one token minted at startup for /auth/token

Q2 ("browser identity") is resolved as planned: a single ui-client class token is minted at startup and held in uiClientToken. /auth/token returns this token (not the server-admin token). In token mode uiClientToken === authToken — unchanged behaviour.

NATS_DATA_DIR fallback to store.dataDir in callout mode

The server process needs NATS_DATA_DIR to call ensureCalloutKeys. If the env var is absent, we fall back to store.dataDir (the app's own data directory). This avoids a hard startup failure for users who haven't set the env var explicitly.

scope-policy.ts dead code cleanup

The runnerForeignKvSubject() helper was left unused in Stage A (the deny-list approach it was designed for was abandoned in favour of allow-only lists — see Stage A notes). It was not flagged by the Stage A typecheck run but surfaced as TS6133 in Stage B. Removed to keep the typecheck gate clean. Recorded as Stage A friction.

Scope widening (Stage B fix)

PILOT: runner pub allow includes $JS.API.> — narrow in Stage D

Root cause: the runner's pub allow-list was missing $JS.API.>. kvm.open(RUNNER_REGISTRY_BUCKET) publishes to $JS.API.STREAM.INFO.KV_* and possibly consumer-create subjects. With only the KV data key in pub allow, nats.js reported "jetstream is not enabled" and the runner never registered, causing waitForRegistration to time out after 15s and crash the server.

Fix — two parts:

  1. Server pre-creates the KV bucket (ensureRunnerRegistryBucket in nats-streams.ts, called from the startup stream-setup block alongside the existing KANNA_* streams). This removes the runner's need for STREAM.CREATE.
  2. $JS.API.> added to runner pub allow as a pilot allowance. A runner can publish to any JetStream API subject — including those for other streams. Cross-runner isolation on runtime subjects (cmd, KV key) is unaffected. Stage D must narrow this to the specific subjects required for kvm.open + kvStore.put, confirmed via nats-server -DV trace.

Integration test re-run after widening: 47/47 pass. runner-A still denied on runtime.runner.cmd.runner-B.* and $KV.runtime_runner_registry.runner-B. The JS API widening does not open a cross-runner hole on the runtime subject plane.

Deviations from Stage B plan

Scope widening required (runner $JS.API.> pub)

The architecture spec said "widen minimally — note what you added and why." The runner's initial pub allow was too narrow: KV open publishes to JetStream API subjects not covered. Added $JS.API.> as the pilot allowance. Also added ensureRunnerRegistryBucket at server startup (not in the original spec, but required to let the runner avoid STREAM.CREATE). Both are flagged for Stage D narrowing.

Design decisions (Stage C)

Bind path was already correct — no data-flow fix needed

hostname flows from startServer(options.host) (driven by --remote/--host CLI flags or the NATS_HOST env) → ensureDaemon({ host: hostname }) → NATS_HOST env on the daemon child → buildCalloutConfig({ host }) → both the TCP host: line and the websocket { host } block. Both listeners bind to whatever the caller passes. Stage C is purely additive: guard + docs.

Guard wired as a startup throw, not a flag

requiresCalloutForBind(hostname, authMode) is called immediately after authMode is resolved, before the daemon is started. If disallowed, startServer throws — the process exits with a clear error before any NATS process is spawned. This is the earliest possible gate: no partial state left behind.

NATS_ADVERTISED_HOST was already wired in /auth/token

/auth/token already reads NATS_ADVERTISED_HOST and returns ws://<advertisedHost>:<wsPort> in the response when set. PR1 Stage C only needed to verify this and document the env vars. Off-box runner connect URL (via env) is PR2; PR1 runners are server-spawned and local.
