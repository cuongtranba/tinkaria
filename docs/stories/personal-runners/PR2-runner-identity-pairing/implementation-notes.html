PR2 — Runner Identity & Pairing

Working narrative · Stage 1 complete — server endpoints + code store + durable token mint

Contract: execplan.md / overview.md / design.md / validation.md; decision 0008. Stacks on PR1's auth-callout.

The pivotal finding

No user-identity system exists

The app is single-tenant — no TinkariaUser, no login/session, only machine name. The concept's "bind a runner to their TinkariaUser" is therefore un-buildable as written. Human decision: build pairing, defer ownerId — a paired runner is "a known external runner" with no owner concept. The token payload stays PR1's {c,r} so o:ownerId is a non-breaking add later.

Design decisions

Durable credential = PR1 token (stateless)

The runner's durable secret IS a PR1 {c:"runner", r:runnerId} token (long TTL), self-verifying via the callout. So the server keeps no per-runner secret store — only the short-lived pairing code. Paired runners reuse the exact PR1 runner scope (no widening).

Code is the bearer secret

The endpoints are unauthenticated (no user system, same posture as /auth/token). Safety rests on the code: short TTL, single-use, unguessable, atomic consume. Gating on user-auth is the documented pre-multi-tenant follow-up.

Open questions (with recommendations)

Q1 — durable token TTL vs refresh

A 90d token means re-pair after expiry. Recommendation: long TTL + re-pair for the pilot; a refresh endpoint (runner presents current token → fresh one) is a follow-up. Confirm 90d default is acceptable.

Q2 — code store durability

In-memory code store loses pending codes on server restart (10-min window). Recommendation: acceptable for pilot; EventStore-persist later if it bites.

Stage 1 — Server Implementation

token.ts — TTL + byteOffset fixes

Added exp field to the token payload (required — legacy tokens without exp are rejected). Added optional ttlSeconds parameter to mintCredentialToken (default 30 days for existing callers; paired runners use RUNNER_PAIR_TTL default 90d). Fixed a pre-existing byteOffset bug in hmacSign/hmacVerify where pooled-Buffer sub-array views caused HMAC key import to see the wrong bytes — fixed with buffer.slice(byteOffset, byteOffset+byteLength).

pairing-store.ts — in-memory single-use code store

Pure class with injectable clock and RNG. Generates 10 random bytes → 16 base32 chars formatted xxxxx-xxxxx-xxxxxx (5-5-6). exchange() looks up the entry before sweeping so "expired" and "consumed" are distinguishable from "unknown". Sweep runs on issue() and exchange() to bound memory growth. 10 unit tests covering shape, uniqueness, single-use, expiry, and sweep semantics.

server.ts — endpoint wiring

Added mintPairedRunnerToken (callout branch only, uses RUNNER_PAIR_TTL env, default 7776000s). Instantiated PairingStore. Two routes inserted before /api/workspace/: POST /api/pairing/code (allocates runner-{ms}-{pid} runnerId, mints long-lived token, stores code, returns {code, expiresAt}) and POST /api/pairing/exchange (atomically consumes code, returns {runnerId, token, natsUrl, natsWsUrl}; 410 expired/consumed; 400 unknown). Token mode returns 409 with a clear message.

Deviations

Fixed pre-existing byteOffset bug in token.ts

The task brief said "do not modify scope-policy.ts or the callout." token.ts was fair game and had a pre-existing test failure (byteOffset). Fixed it as part of adding TTL — all 13 token tests now pass.
