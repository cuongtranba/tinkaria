Design decisions

Unify on port-claude's runner-side resolver

port-claude's PTY path already resolves the binary runner-side (resolve-binary.adapter, no binaryPath param). PR4 drops binaryPath from StartTurnCommand and routes Codex + Claude SDK through the SAME resolver — not a second one. For Codex, a thin resolveCodexBinary() wraps which codex (no separate adapter needed; Codex has no node_modules fallback path like the Claude SDK does).

Injectable resolver for testability

startClaudeTurn accepts _resolveBinary? (underscore-prefixed per convention for test seams). Production path uses the real adapter; tests inject a synchronous fake to avoid real PATH/fs probes. The PTY path already owns a real integration test (resolve-binary.test.ts).

Secrets never transit the server

extraEnv = profile non-secret env only. Formalized as a type doc comment + runtime audit guard (regex detects API_KEY|TOKEN|SECRET|Bearer|sk- patterns in keys/values). Secrets stay runner-side (local env + OAuth pool).

Refuse, don't route (PR4 vs PR5)

PR4 scope: drop binaryPath + unify binary resolution. Capability probe + gate (Stage 2) and multi-runner routing (PR5) are separate work items, not touched here.

Open questions (with recommendations)

Q1 — capability probe depth (Stage 2)

Probe just provider-binary existence, or also models (via RuntimeRegistry.probeCapabilities)? Recommendation: providers + models (reuse the existing probe); gate on provider for PR4, model-level gate if cheap.

Deviations from plan

createClaudeOptions made async

The function was sync before; making it async to call resolveClaudeBinary is a natural consequence. startClaudeTurn was already async so callers are unaffected. No behavioral change beyond the binary now being resolved inside the function rather than passed in.

Deferred

Stage 2: capability probe + advertise + turn-start gate. Stage 3: dual-signal E2E verify + security review. Multi-runner routing (PR5); general local secret vault; ownerId.
