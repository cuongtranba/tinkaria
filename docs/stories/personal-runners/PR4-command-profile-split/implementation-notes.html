Design decisions

Unify on port-claude's runner-side resolver

port-claude's PTY path already resolves the binary runner-side (resolve-binary.adapter, no binaryPath param). PR4 drops binaryPath from StartTurnCommand and routes Codex + Claude SDK through the SAME resolver — not a second one (avoids the divergence the explore flagged).

Secrets never transit the server

extraEnv = profile non-secret env only (today apiKeyRef isn't expanded, so this formalizes an accident into an enforced invariant + an audit guard). Secrets resolved runner-side (local env + OAuth pool).

Refuse, don't route (PR4 vs PR5)

PR4 advertises probed capabilities + refuses a turn the single active runner can't honor (reusing PR3's gate). Choosing among multiple capable runners is PR5 (routing).

Open questions (with recommendations)

Q1 — capability probe depth

Probe just provider-binary existence, or also models (via RuntimeRegistry.probeCapabilities)? Recommendation: providers + models (reuse the existing probe); gate on provider for PR4, model-level gate if cheap.

Q2 — port-claude PTY resolver reuse

Reuse resolve-binary.adapter as-is for Codex/Claude SDK, or wrap it? Recommendation: reuse directly; only wrap if the interface doesn't fit — do not modify the PTY path's behavior.

Deferred

Multi-runner routing (PR5); general local secret vault; ownerId.
