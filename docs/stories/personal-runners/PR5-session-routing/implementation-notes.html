Design decisions (where the spec was ambiguous)

Lane: normal → high-risk

The change-request pre-triaged PR5 normal. We lane up because the realized change rewires the turn-dispatch chokepoint (RunnerProxy) from a fixed runnerId to per-session selection — large Existing-behavior blast radius across server+client+protocol. No hard gate fires (so it's judgment, not forced); when pre-triage and realized blast radius disagree, lane up. Same care as PR1–PR4.

Sticky pin (persisted) vs per-turn selection

Chosen: persist chat.runnerId, select once, honor for the chat's life, recompute only when the pinned runner is no longer eligible. A turn + its cancel + tool responses + PTY teardown must reach the same machine (the session's claude-pty child / OAuth pool / MCP server live there). Per-turn re-selection could strand an in-flight session. This is the concept's "sticky-default."

Shared-runner fallback not special-cased

The server-spawned runner is just another list() entry flagged isShared. A member with no personal runner finds it as the sole eligible candidate → auto-selected. Avoids a separate fallback branch.

Fail-closed liveness/compat, fail-open capability

Offline + incompatible runners are never eligible (fail-closed). capabilities===null (pre-PR4 runner) is treated capable (fail-open) — matching PR4; the turn-start capability gate still catches a real mismatch loudly. Avoids excluding older runners that simply haven't probed yet.

Tradeoffs

  • No list() caching. Selection reads KV each turn-start (cheap, infrequent). Caching risks routing to a just-died runner. Revisit only if hot.
  • Superset constraint over clean rewrite. RunnerProxy must keep single-runner behavior bit-identical (existing runner-proxy.test.ts green unchanged) rather than a from-scratch multi-runner proxy — lower blast radius, provable.

Deviations from plan

  • Lane: took PR5 as high-risk though the change-request pre-triaged it normal (rationale in overview/decision 0011).
  • getRunnerReadiness kept synchronous (design left it open). Shared/local runner → live runnerManager.getReadiness(); a selected personal runner → {incompatible:false, capabilities:null} (fail-open). Safe because select() already enforced !incompatible && state!=="offline" && capable before returning selected — the gate is redundant for an already-selected runner, and avoiding async kept blast radius off every caller of the sync getHealthcheck.
  • Empty-candidate needs_pick → fail-fast. design.md ordered the sticky-offline check before the empty check, so a gone sticky pin with zero other eligible yields needs_pick with empty candidates. resolveRunnerForChat guards this: empty candidates → a plain fail-fast Error (no dead-end picker), non-empty → RunnerPickRequired.
  • /health runners[] computed at the route (not in sync getHealthcheck) with .catch(()=>[]) — zero blast radius on existing healthcheck callers.
  • Runner indicator is best-effort local (last-8 of runnerId, resets on navigation). A live name needs runnerId in ChatSnapshot — out of scope per the design's "minimal" guidance.

Code review outcomes (ecc:typescript-reviewer)

Fixed (commit 76d9df1):

  • Persist-after-dispatch (HIGH) — resolveRunnerForChat no longer persists the pin before dispatch; returns {runnerId, shouldPersist} and callers persist only after sendCommand succeeds, so a failed dispatch can't strand a chat on an unreachable runner.
  • Client retry re-opens picker (HIGH) — if the post-pick retry itself returns needsPick (picked runner went ineligible), the dialog re-opens instead of closing silently.
  • Per-entry JSON.parse guard (MED) in RunnerRouter.list() — one corrupt KV value can't truncate the fleet.
  • Dialog state reset (MED) — RunnerPickerDialog clears selected/error/busy on a new request.

Consciously deferred / dispositioned:

  • Start-turn race (reviewer HIGH) — re-analyzed as not a divergent-dispatch bug: with no pin, two concurrent starts run select() on the same registry → either 1 eligible (both resolve to the same runner = the pre-existing single-runner double-send, already guarded by recentlyStartedChats) or ≥2 eligible (→ needs_pick, no dispatch). Persist-after-dispatch narrows the window further. No per-chat mutex added (would be over-engineering for this path).
  • O(n) serial KV get() on every start_turn (MED) — folded into HARNESS_BACKLOG #6 (registry no-TTL / enumeration cost); ties to capping the 213-entry registry.
  • Anonymous-type casts for protocolVersion/ownerId (MED) — left; declaring ownerId? on RunnerRegistration belongs with the deferred ownerId work (PR2 deferral). protocolVersion is already typed on the registration.
  • Fail-open protocolVersion:null for personal runners (MED) — cosmetic (error string only); the gate is redundant post-select(). Left as documented.
  • dispose-on-missed-pin leak (LOW) + indicator naming (NIT) — edge/cosmetic; noted, not fixed.
