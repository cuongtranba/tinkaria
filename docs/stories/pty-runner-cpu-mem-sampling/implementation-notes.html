pty-runner-cpu-mem-sampling normal lane

Make runner-spawned claude-pty instances surface live CPU% and resident memory (current + session peak) to the PtyInstancesIndicator UI.

Root cause

Tinkaria runs PTY two ways:

PathEntrySampler wired?
Server (single-process, kanna-style)pty-responders.tsYes — passes ptyInstanceRegistry; sampler upserts → delta
Runner (live execution process)turn-factories.ts startClaudePtyTurnNo — passed only ptyRegistry (on-disk pid registry)

The driver memory sampler upserts into args.ptyInstanceRegistry?.upsert(...). On the runner path that arg is undefined, so every ps sample was computed then discarded. The runner publishes deltas manually from a baseInstance whose rssBytes/cpuPercent were hardcoded null — so the UI received every field except cpu/mem (and the UI gates those rows on !== null). Kanna worked because it only ever ran the single-process server path.

Design decisions

  • Callback over registry (user-approved). Added an optional onUsageSample callback to StartClaudeSessionPtyArgs. The sampler tick invokes it alongside the existing ptyInstanceRegistry.upsert, passing the same {rss, rssPeak, cpu, cpuPeak}. Additive; the server path is untouched. Avoids giving the runner a second registry whose deltas would race the manual ones.
  • baseInstance becomes the canonical mutable record. Phase transitions now mutate baseInstance.phase (instead of inline spread overrides) so a usage delta published between transitions carries the correct current phase, not a stale spawning.
  • Stop-flag guard. The store re-adds an instance on an updated delta for an unknown live chatId. A stray sampler tick after teardown/abort could resurrect a removed instance. usageStopped (flipped on spawn failure and via session.stopUsage() in the reader's finally) suppresses late samples.
