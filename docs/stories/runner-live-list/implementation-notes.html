US-RLL — Runners tab live list normal lane

Working narrative. Contract lives in story.md beside this file.

What the user asked for

"Real-time status update of the pairing — the instance would appear on the UI after the command executed and connected." The Runners tab previously had only a "Generate pairing code" button: a runner could connect and the tab would never show it.

Design decisions

  • Reuse GET /health, poll every 2s. /health already returns runners[] (the server's RunnerDescriptor), is public, and needs no server change. A 2s client poll surfaces a new runner within ~2s of it registering. Chose polling over a NATS KV-watch over the browser socket: the KV registry has ~220 stale tombstones (no TTL), so a watch would stream noise on connect, and polling is far simpler for a settings tab that's open briefly. (KV-watch remains an option if we ever want sub-second.)
  • Filter to relevant runners (!incompatible && state !== "offline"), online sorted before degraded. Without this the list is ~220 dead tombstones. Filtering lives in a pure helper, unit-tested.
  • "Just connected" = a relevant runnerId not present when the code was generated. We snapshot the relevant ids into a ref at code-gen; any new id is highlighted (green ring + "connected" badge). Until one appears, a dashed "Waiting for a runner to connect…" row shows.
  • Prefill the command with window.location.origin instead of the old <server-url> placeholder — copy-paste-ready.

Deviations

None. Scope held to "live list + connect feedback" (the option chosen). The command-prefill was a tiny adjacent improvement folded in (it's the same code block and was actively misleading with the placeholder).
