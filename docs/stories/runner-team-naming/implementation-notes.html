US-RTN — Runner naming + team management & assignment

Decision: .c3/adr/adr-20260528-runner-naming-and-team-assignment.md · Lane: normal · Intake #23

What & why

Operator can (1) name each runner inline on the Runners tab, (2) manage a flat list of "members" (labels only — no auth) in a new Team tab, and (3) assign a member to a runner. Display/grouping only — runner routing/eligibility is untouched. Confirmed with the user up front: members are labels (no accounts), assignment is cosmetic, persistence "my call".

Design decisions

DecisionWhy
Persist via EventStore (runner-teams.jsonl + state maps + NATS runner-teams snapshot + team.member.*/runner.label.* commands), not a new KV bucket. Mirrors the sibling Provider Profiles settings surface exactly. The runner-owned runtime_runner_registry KV is rewritten on every heartbeat (updateLastSeenAt spreads this.registration) → it would clobber any server-set field. Operator config is a different ownership domain. EventStore gives durable replay + live snapshot plumbing for free.
Pure join helpers (resolveRunnerName, resolveRunnerMember) live in src/shared/runner-team-types.ts. Both display consumers (RunnersTab via /health, RunnerPickerDialog via the pick request) key off runnerId; the join is client-side against the snapshot. Shared + pure = unit-testable, reusable.
runner_label_set is an upsert keyed by runnerId (name + memberId together). One record per runner. Naming (Runners tab) and assignment (Team tab) both write the same record, each preserving the other's field.
team_member_removed cascades: unassign runners pointing at it (memberId → null, name preserved). Mirrors how provider_profile_removed cascades into overrides. Avoids dangling memberId references.
Snapshot persistence: added teamMembers/runnerLabels to SnapshotFile + save/load/reset. Compaction truncates the jsonl logs; without snapshot persistence a compaction would silently drop the data (the data-loss trap that profiles already guard against).

Deviations from the original ADR

  • Naming UX moved to inline on the Runners tab (user choice); the Team tab owns members + the per-runner assignment dropdown only. ADR L8/L9 updated to match before coding.
  • RunnerPickerDialog gained an optional socket prop so it can subscribe to runner-teams itself (keeps ChatPage change to one line; dialog is self-sufficient).
  • RunnersTab now takes a state prop (was prop-less) for socket access; useLiveRunners exported so the Team tab reuses the /health poll instead of duplicating it.

A5 blocker — browser E2E not completed

The CLAUDE.md dual-signal rule wants a running-app proof. I could not complete it:

  • The live prod instance occupies :3210. Per the boot-isolation memory I booted the worktree on the dev profile (separate data dir + NATS).
  • The dev server fails at ensureDaemon: "NATS daemon produced no output" → nats-server exited with code 1 before ready.
  • Diagnosis: an isolated async-spawn repro (same callout config, same binary, same dev env) boots nats-server successfully (jetstream restores streams, stays up). So nats-server + the generated config are fine in this environment — the failure is in the dev.ts/nats-daemon-manager spawn path when a second instance co-runs with the live one. Cause not fully pinned (would require instrumenting src/nats/nats-daemon-callout.ts, which I avoided as out-of-scope and risky next to the live instance).
  • Incident: during diagnosis a pkill -f "nats-daemon" matched and killed the prod callout daemon, taking :3210 to 503. The user restarted prod (new PID, healthy 200). Dev profile data was backed up and restored to its original state.

Why confidence is still high without A5: A2 exercises the exact 5 WS commands the UI calls, over a real embedded NATS server + real EventStore, asserting state mutation, the mutating-command broadcast trigger, and the member-removal cascade. A1 covers reducer + replay + compaction round-trip. A4 covers the client join logic. The only unproven slice is React render/event wiring, which is type-checked and thin.
