runner-ws-transport high-risk

Working narrative. Contract in overview/execplan/design/validation.md.

The bug, end of a long hunt

A remote runner over the tailnet connects, heartbeats (→ "online"), and does JetStream request/reply — but never receives server-initiated start_turn pushes, so every turn times out. Confirmed via NATS /connz: the runner's command subscriptions ARE registered server-side (cid=2242, pending_bytes=0), yet delivery to the raw :4222 tailnet connection fails. The browser works because it rides the server's /nats-ws proxy over the single tunneled port (3210).

Fix

Route the runner through the same /nats-ws proxy as the browser. The runner derives wss://<host>/nats-ws from the server URL it paired against, and connects via wsconnect (@nats-io/nats-core; Bun has a global WebSocket). Its NATS connection then terminates at the server-local proxy (appears as 127.0.0.1), so server→runner delivery is local and reliable; the tailnet hop is the tunneled HTTP.

runner-credential.ts  + natsWsProxyUrl?: string
runner-pair.ts        derive wss://host/nats-ws from serverUrl, store it
runner-nats.ts        connectRunner: ws/wss -> wsconnect, else TCP connect
runner.ts             prefer cred.natsWsProxyUrl over cred.natsUrl

Design decisions

  • Runner derives the proxy URL, no server change. The runner already knows the server URL it paired against; deriving wss://host/nats-ws avoids touching the pairing response and matches the browser's own derivation.
  • TCP fallback kept. Older credentials (no natsWsProxyUrl) and env-driven local runners (NATS_URL) keep using raw TCP — loopback, where it works fine. Only paired/remote runners switch to WS.
  • wsconnect is Kvm/JetStream-compatible — verified locally: the WS runner registered in KV and subscribed, identical to the TCP path.

Verification (local — connection level)

typecheck exit 0; runner-pair/nats/credential tests pass (+ derivation assertion)
dev boot: paired runner credential has natsWsProxyUrl=ws://127.0.0.1:5179/nats-ws
/connz: runner connected as cid=57 ip=127.0.0.1 lang=nats.ws, all 5 cmd subs registered
  (i.e. now a local proxied connection, like the browser — not a raw tailnet socket)

Open

Remote turn-completion is pending operator verification. Local proves the WS transport + registration work and that the runner now connects as a proxied/local connection, but local TCP already worked, so it can't prove the tailnet fix. The operator re-pairs the remote runner (to get natsWsProxyUrl), restarts it, and sends a turn; it should complete with no start_turn timeout. Confirm via VL + /connz (runner now 127.0.0.1/nats.ws).
